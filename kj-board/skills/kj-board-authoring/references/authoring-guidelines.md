# KJ Board: オーサリング設計ガイド

この資料は、添付元 `kj-session-board-json-authoring` の品質基準・配置原則を、グループ／接続線のない現行 KJ Board 用に再編したものである。データ形式の規範は [`board-format.md`](board-format.md) を優先する。

## 1. 三階層コピーの詳細

### Layer 1 — `title` （識別）

- 日本語ならおおむね6〜18文字、名詞句・短い問い・技術用語を優先する。
- 良い例: `ルートはどう決まる？`、`ミドルウェアの順序`、`失敗時の流れ`、`最小の Express`
- 避ける例: `Express.js におけるルーティング処理の詳細について`、`重要`、`ポイント`、`説明`
- 同じ学習段階内で粒度をそろえ、詳細な結論をタイトルに書かない。

### Layer 2 — `text` （誘導）

- 原則1〜2行。具体語を一つ以上使い、Why / How / Difference のいずれかを匂わせる。
- 良い例: `上から順に実行される。では next() は何を渡す？`、`3行のコードから処理の全体像を見る`
- 避ける例: `詳しくはポップアップを見てください`、`Express.js の説明です`、長い箇条書きやコード全文。
- 目的は「ポップアップを読みたい」と思わせることであって、中身の要約を全て置くことではない。

### Layer 3 — `markdownSource` / `inline` / `imageUrl` （核心）

- **Markdown**: 結論2〜3文 → 仕組み・原因 → 実務で確認する点。必要に応じて比較表、Before/After、箇条書き、注意、典拠を加える。
- **Code**: 最小の動作単位。不要なboilerplateを除き、コメントは「なぜ」を説明する。`language` を実際の言語に合わせる。
- **Mermaid**: 一図一メッセージ。構造・処理・状態・順序を可視化。ノードが多いとPDFで小さくなるので複数枚へ分割する。
- **Image**: 実画像でなければ伝わらない価値があるときだけ使う。`title` / `text` は画像を見る観点を示す。

## 2. 付箋の役割設計

| Note role | 用途 | 推奨 type |
| --- | --- | --- |
| Concept | 前提・概念の導入 | markdown |
| Question | 疑問を提起して次へつなぐ | markdown |
| Example | 挙動の具体化 | markdown / code |
| Code | 実行例・設定断片 | code |
| Flow | 処理の通り道 | mermaid |
| Comparison | 2つ以上の特徴の違い | markdown（GFM 表）|
| Pitfall | 失敗・例外・注意 | markdown / code |
| Practice | 次に試す操作 | markdown / code |

同じ核心を markdown / code / mermaid へ無意味に複製せず、**説明・実装・構造**という異なる視点にする。

## 3. 意味的近さ（Affinity）

内部設計時に、任意の付箋ペアに0〜3の類縁度を割り当てる。

| Score | 意味 | 配置 |
| --- | --- | --- |
| 3 | 直接つながる／同じ理解単位 | 隣接、約30〜45pxの隙間 |
| 2 | 同じ学習クラスタだが別観点 | 近接、約45〜70px |
| 1 | 章をまたいで関連 | 段階を分けつつ視線がつながる位置 |
| 0 | 直接は関連しない | 意図的な余白を確保 |

上記は座標間距離ではなく、付箋矩形間の**見た目の空白量**の目安。高さの自動調整と表示幅を考慮する。

## 4. クラスタ配置（現行版）

旧版では groups と edges によって章境界や関係を表現していたが、現在はどちらも廃止されている。**類似付箋の配置・連続した行・空白**を使って同じ情報設計上の役割を表現する。

- 基礎 → 詳細、問い → 仕組み → 実践、入力 → 処理 → 出力、正常系 → 例外系などの学習順序を選ぶ。
- ひとつの段階では「解説 → コード → 描画」を横並びに配置できる。
- 次の段階は下の行に置き、区切りとなる余白を確保する。
- `x,y` はなるべく5または10px単位に丸める。
- 基本付箋幅は220pxを想定し、開始位置は x=80、y=180 程度を推奨する。
- 同じ段の座標をそろえる。PDF目次は上→下、同じ段で左→右なので**配置はそのまま印刷時の読順**になる。
- Z順は重なり順専用。重なりそのものは通常避ける。

### モデル配置例（12枚）

```text
  x=80                350               620
┌───────────────────────────────────────────┐
│ 01. 基本の骨格                             │
│ [Markdown 解説] [Code ソース] [Mermaid 図] │ y=180
│                                           │
│ 02. メッセージ                             │
│ [Markdown 解説] [Code ソース] [Mermaid 図] │ y=420
│                                           │
│ 03. 制御構造                               │
│ [Markdown 解説] [Code ソース] [Mermaid 図] │ y=660
│                                           │
│ 04. 読みやすくする                         │
│ [Markdown 解説] [Code ソース] [Mermaid 図] │ y=900
└───────────────────────────────────────────┘
```

**この枠線や見出しは計画用の図**であり、アプリへ `groups` を生成する意味ではない。実際の表示には各付箋の `title` / `text` を使う。

## 5. 色彩戦略

| Color | Value | 意味の例 |
| --- | --- | --- |
| Yellow | `#FFF2A8` | 基礎・問い |
| Blue | `#DCEEFF` | 仕組み・構造 |
| Green | `#DDF4D2` | 実装・成功例 |
| Orange | `#FFE0C2` | 境界・注意 |
| Pink | `#F7DDF1` | 失敗・アンチパターン |
| Purple | `#E9E0FF` | 発展・設計判断 |

色は補助。意味を色だけに託さず、**配置・文章・タイプとの一貫性**を優先する。

## 6. 研究・情報の正確性

ユーザー提供資料を第一資料とする。最新の仕様やバージョン依存事項は可能なら信頼できる一次資料で確認する。バージョンを明記し、確認できない事項は仮説と区別する。興味を引く `text` で断定や誇張を使わない。技術的典拠は Markdown ポップアップ内にURLで示す。

## 7. 品質確認表

- [ ] 1 note = 1 central idea
- [ ] `title` により対象が瞬時に分かる
- [ ] `text` により詳細を開く理由ができる
- [ ] popup 単体で疑問が解消する
- [ ] 各付箋の `text` と popup が同じ説明の反復ではない
- [ ] 同じ段の x/y がそろい、異なる段階は空白で区別される
- [ ] 付箋矩形の衝突がない
- [ ] PDF目次の読順が自然である
- [ ] 4タイプ以外・旧版groups/edgesを含めない
- [ ] Codeの言語名、Mermaidソース、画像URLを確認した
- [ ] `validate_board.py --strict` が成功した

## 8. 参照ボードの学び方

`reference-board.json` は、元スキルの Mermaid Sequence Diagram 教材（4グループ×3付箋）から、原文と Mermaid/Code ソースを保ったまま **4行×3列**へ変換した。

- 各段階の **Markdown** は概念と公式資料へのリンクを提供
- **Code** は Mermaid 構文をプレーンテキストとして見せる
- **Mermaid** は同じ構文を図としてレンダリングする
- 段階の進行（基本 → メッセージ → 制御 → 読みやすさ）は上から下へ配置
- PDF目次でも「解説 → ソース → 描画」の順に並ぶ

公式仕様: https://mermaid.ai/open-source/syntax/sequenceDiagram.html
